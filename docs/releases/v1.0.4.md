# wayland-vnc v1.0.4

A packaging and lab release. The `wayland-vnc` package behaves exactly as in v1.0.3:
the payload, the hardened systemd **user** unit, the default `127.0.0.1:5900` bind and
the Local Network Access switch. The GNOME backend `wayland-vnc-grd` is as in v1.0.1.
What changes is that the Snap and the Flatpak now reach the release for both
architectures, and the Android qualification lab says when it is not ready instead of
producing a record that blames the viewer.

## Install

### Ubuntu 26.04 (PPA)

The release tag uploads two source packages to `ppa:ventura8/wayland-vnc`
(Launchpad builds them shortly after): `wayland-vnc`, and for GNOME desktops the patched
GNOME Remote Desktop backend `wayland-vnc-grd`, built from the pinned upstream sources.
Their changelogs say what the release gate found: for this release, *not
release-qualified*.

```sh
sudo add-apt-repository ppa:ventura8/wayland-vnc
sudo apt update && sudo apt install wayland-vnc
sudo apt install wayland-vnc-grd   # GNOME desktops
```

### GitHub release assets

Every release publishes `.deb`, `.rpm` (Fedora/EL/openSUSE), Arch `.pkg.tar.zst`,
AppImage, Flatpak, and Snap binaries plus a `SHA256SUMS` manifest. The AppImage, the
Flatpak, the Snap and the GNOME backend come once per architecture:

| Format | amd64 | arm64 |
| --- | --- | --- |
| AppImage | `wayland-vnc-1.0.4-x86_64.AppImage` | `wayland-vnc-1.0.4-aarch64.AppImage` |
| Flatpak | `wayland-vnc-1.0.4-x86_64.flatpak` | `wayland-vnc-1.0.4-aarch64.flatpak` |
| Snap | `wayland-vnc_1.0.4_amd64.snap` | `wayland-vnc_1.0.4_arm64.snap` |
| GNOME backend | `wayland-vnc-grd_1.0.4_amd64.deb` | `wayland-vnc-grd_1.0.4_arm64.deb` |

Verify before installing a downloaded asset:

```bash
sha256sum --ignore-missing -c SHA256SUMS   # checks only the assets you downloaded
sudo apt install ./wayland-vnc_1.0.4_all.deb           # Debian/Ubuntu
sudo dnf install ./wayland-vnc-1.0.4-1.*.noarch.rpm    # Fedora/EL
```

On a GNOME desktop that does not use the PPA, also install the patched GNOME Remote
Desktop backend from the assets; the distribution's own crashes whenever a viewer
disconnects:

```bash
sudo apt install ./wayland-vnc-grd_1.0.4_amd64.deb
```

## What is in this release

### The Snap and the Flatpak for both architectures

Both are built on an amd64 and an arm64 runner, but their names -- `wayland-vnc_<v>.snap`
and `wayland-vnc-<v>.flatpak` -- carried no architecture, and the release job downloaded
every runner's files into one directory. One runner's bundle replaced the other's
without a word, so v1.0.0 to v1.0.3 each shipped a single `.snap` and a single
`.flatpak`, whichever architecture happened to land last.

They are now named per architecture, the way each ecosystem spells it:
`wayland-vnc_<v>_<amd64|arm64>.snap` and `wayland-vnc-<v>-<x86_64|aarch64>.flatpak`
([`scripts/build_release_package.sh`](../../scripts/build_release_package.sh); the
portable smoke names its snap the same way). The release job keeps each build job's
files in a directory of its own and fails on a file name two jobs produced, so a name
collision can no longer cost an asset silently. The tests run the job's own assembly
step, taken from the workflow.

### The Android lab says when it is not ready

The Android emulator does not survive a reboot, and the qualification runner does not
start it. With no emulator attached, a run went ahead anyway: every scenario failed on
"no valid frame", and the record named the viewer "RealVNC Viewer for Android unknown",
which read as a viewer defect. It cost a GNOME and a Hyprland run in the v1.0.2
campaign.

`AndroidViewer.lab_problem` now checks the device at `emulator-5554`, a console that
answers `adb emu avd name` with the lab AVD (the two-finger gestures and the rotation
go through it), a finished boot, and the installed app. The Android drivers ask it
before the fixture or the KVM guest starts, and stop naming the fix -- start the lab
with `scripts/android-stage.sh`, or provision the viewer.

### The headless container lab works with the runner

[`scripts/android-emulator.sh`](../../scripts/android-emulator.sh) runs the same AVD
headless in an unprivileged container. Its emulator wrote a fresh console token into
the container's own home, so the host's `adb emu` was refused every time and the
runner could not drive it. The container now shares the host's token
(`~/.emulator_console_auth_token`, created private if missing, mounted read-only).
`start` clears the lock files a lab stopped from outside leaves in the AVD directory,
only when no emulator is running the AVD, and `stop` shuts the emulator down through
its console before falling back to `docker stop` -- six seconds instead of a minute,
with no lock left to block the next boot.

## Compatibility status

**No desktop is release-qualified at this tag.** `qualification/records.json` is
intentionally empty, and the release gate stays red until all fourteen target/viewer
pairs pass on a trusted runner and their records are published to the evidence store for
the exact commit that is tagged (`docs/evidence-store.md`).

The serving path is unchanged since v1.0.2, whose branch was validated on real hardware
and in the KVM campaign with the actual RealVNC viewers (see
[v1.0.2](v1.0.2.md#compatibility-status)): Sway, Wayfire, Xfce on labwc, LXQt on labwc
and KDE Plasma passed with both viewers; GNOME all but `lock`, which GNOME Shell refuses
by design; Hyprland is blocked by an upstream aquamarine defect on a live switch to 4K.
Those runs were on earlier commits, so they are not evidence for this tag.
